    Fases del desarrollo de una aplicación¶

    El desarrollo de una aplicación informática no es un proceso improvisado, sino una actividad planificada, estructurada y metódica que implica una serie de fases bien definidas. Cada una de estas etapas cumple un propósito concreto dentro del ciclo de vida del software y permite avanzar desde la idea inicial hasta el producto final que utilizan los usuarios.

    Análisis de requisitos¶

    Toda aplicación nace de una necesidad, ya sea de una empresa, una institución o un usuario final. En esta primera fase se lleva a cabo un estudio detallado de esa necesidad para determinar qué problema se va a resolver y qué funcionalidades deberá tener el sistema.

    El analista de software recopila información mediante entrevistas, cuestionarios o reuniones con el cliente. Posteriormente, redacta un documento de requisitos que recoge:

    • Requisitos funcionales: qué debe hacer el sistema.
    • Requisitos no funcionales: rendimiento, seguridad, usabilidad.
    • Restricciones técnicas: hardware, software o entorno.

    El resultado de esta fase es un conjunto de especificaciones claras que servirán como punto de referencia durante todo el desarrollo.

    Consejo

    Una mala definición de requisitos suele ser la causa principal de errores o fracasos en los proyectos de software.

    Diseño del sistema¶

    Una vez definidos los requisitos, se pasa a la fase de diseño, en la que se planifica cómo se construirá la aplicación. Aquí se definen la arquitectura del software, la estructura de datos, los flujos de información y la interfaz de usuario.

    El diseño puede dividirse en dos niveles:

    • Diseño de alto nivel: define los módulos del sistema, sus relaciones y la arquitectura general (por ejemplo, cliente-servidor o MVC).
    • Diseño de bajo nivel: especifica las estructuras de datos, los algoritmos y la lógica interna de cada módulo.

    Durante esta fase se suelen utilizar diagramas UML, esquemas de base de datos y prototipos de interfaz (mockups). El objetivo es ofrecer una representación visual y comprensible del sistema antes de empezar a programar.

    Implementación o codificación¶

    La fase de implementación consiste en transformar los diseños en código fuente mediante un lenguaje de programación. Es el momento en que los desarrolladores convierten los diagramas y estructuras en un conjunto de instrucciones que el ordenador puede ejecutar.

    En esta etapa se eligen las tecnologías y herramientas más adecuadas (lenguaje, frameworks, bases de datos, IDE, control de versiones, etc.), y el equipo de desarrollo trabaja colaborativamente siguiendo buenas prácticas de programación:

    • Claridad y legibilidad del código.
    • Uso de comentarios y convenciones de nombres.
    • Modularización y reutilización de componentes.
    • Control de versiones con Git.

    Ejemplo

    En un proyecto web moderno, un desarrollador puede implementar el backend en Laravel y el frontend en Vue.js, mientras el control de versiones se gestiona con GitHub.

    Pruebas y verificación¶

    Una vez que el sistema está implementado, comienza la fase de verificación y validación. El objetivo es comprobar que la aplicación funciona correctamente y cumple con los requisitos definidos en la primera fase.

    Se realizan distintos tipos de pruebas:

    • Pruebas unitarias: verifican el funcionamiento individual de cada módulo o función.
    • Pruebas de integración: comprueban que los módulos interactúan correctamente entre sí.
    • Pruebas de sistema: evalúan el comportamiento global del software.
    • Pruebas de aceptación: permiten al cliente o usuario final validar el producto.

    Importante

    Las pruebas no solo detectan errores; también aseguran que el producto cumple los estándares de calidad definidos.

    Despliegue o implementación en producción¶

    Cuando las pruebas se completan con éxito, la aplicación se despliega en el entorno donde será utilizada por los usuarios. Este proceso puede implicar la instalación del software en servidores, la configuración de bases de datos o la publicación en tiendas de aplicaciones.

    En proyectos modernos, esta fase suele gestionarse mediante procesos de integración y entrega continua (CI/CD), que automatizan el despliegue y reducen errores humanos. También se elaboran manuales de instalación, guías de usuario y documentación técnica.

    Mantenimiento y mejora continua¶

    El ciclo de vida del software no termina cuando la aplicación se entrega. Durante su uso real aparecen nuevos requisitos, errores inesperados o necesidades de actualización tecnológica. Por ello, esta fase se centra en mantener y evolucionar el sistema, corrigiendo fallos, optimizando el rendimiento o añadiendo nuevas funcionalidades.

    Existen tres tipos principales de mantenimiento:

    • Correctivo: reparación de errores detectados tras la entrega.
    • Perfectivo: mejora del rendimiento o la eficiencia.
    • Adaptativo: actualización a nuevos entornos o tecnologías.

    Recuerda

    El mantenimiento asegura la sostenibilidad del software a lo largo del tiempo y permite que la aplicación siga siendo útil y competitiva.

    Ejemplo completo: aplicación de reservas de un gimnasio¶

    Para comprender cómo se relacionan las fases, utilizaremos un proyecto común: una aplicación web que permite a los socios de un gimnasio consultar actividades y reservar plazas.

    Fase Trabajo del equipo Entregable
    Análisis Entrevistar al responsable y definir qué necesita el usuario Documento de requisitos e historias de usuario
    Diseño Dibujar pantallas, clases y estructura de la base de datos Prototipos, diagramas UML y modelo de datos
    Implementación Programar las pantallas, la API y el acceso a datos Código fuente versionado
    Pruebas Comprobar reservas, aforo y errores Casos de prueba y resultados
    Despliegue Publicar el servicio y configurar la base de datos Aplicación disponible y guía de instalación
    Mantenimiento Corregir errores y añadir funcionalidades Nuevas versiones y registro de incidencias

    1. Análisis: convertir necesidades en requisitos¶

    El gimnasio solicita que los socios puedan reservar una clase desde el móvil. El equipo debe concretar qué significa reservar correctamente.

    Requisitos funcionales (comportamientos observables):

    • RF-01: el usuario puede iniciar sesión.
    • RF-02: el usuario puede consultar clases y plazas disponibles.
    • RF-03: el usuario puede reservar una plaza si queda aforo.
    • RF-04: el usuario puede cancelar una reserva.

    Requisitos no funcionales (condiciones de calidad):

    • RNF-01: la interfaz debe adaptarse a pantallas móviles.
    • RNF-02: las contraseñas no deben almacenarse en texto plano.
    • RNF-03: las operaciones habituales deben responder en un tiempo aceptable, que el equipo deberá concretar y medir.

    Una historia de usuario puede escribirse así:

    Como socio del gimnasio, quiero reservar una clase desde mi teléfono para asegurar mi plaza sin llamar a recepción.

    Criterios de aceptación: existe una plaza disponible; al reservar se reduce el aforo; si no hay plazas se informa al usuario; un socio no puede duplicar la misma reserva.

    Herramientas habituales: documentos compartidos, formularios, entrevistas, GitHub Issues, Jira o Trello.

    2. Diseño: decidir cómo se construirá¶

    Se propone una arquitectura cliente-servidor:

    flowchart TD
    WEB["Interfaz web: HTML, CSS y JavaScript"]
    API["API REST: Java y Spring Boot"]
    BD[("Base de datos: PostgreSQL")]
    WEB -->|HTTP / JSON| API
    API --> BD

    En el modelo de datos podrían existir las entidades Socio, Clase y Reserva. Una reserva relaciona a un socio con una clase y una fecha. Antes de programar, se definen las relaciones y las restricciones necesarias para evitar duplicados.

    El diseño de interfaz puede comenzar con un wireframe de las pantallas «Listado de clases», «Detalle» y «Mis reservas». Un diagrama de clases UML permite representar atributos, métodos y relaciones entre clases.

    Herramientas habituales: Figma para prototipos, diagrams.net para diagramas y PlantUML o Mermaid para documentar la arquitectura.

    3. Implementación: transformar el diseño en código¶

    En una aplicación Java, la lógica de reservas podría comprobar que aún quedan plazas:

    public boolean puedeReservar(int plazasDisponibles) {
    return plazasDisponibles > 0;
}

    Este ejemplo ilustra una regla básica; en un sistema real también habría que comprobar la identidad del usuario, la existencia de reservas anteriores y la concurrencia para evitar superar el aforo.

    Un endpoint orientativo de la API podría ser:

    POST /api/reservas
Content-Type: application/json

{"socioId": 12, "claseId": 5}

    El equipo puede organizar el código en un repositorio Git, crear ramas para cada funcionalidad y revisar los cambios mediante pull requests antes de integrarlos.

    Tecnologías posibles: Java, Spring Boot, Maven o Gradle, PostgreSQL, IntelliJ IDEA o VS Code, Git y GitHub. Son ejemplos de una pila tecnológica, no herramientas obligatorias para cualquier proyecto.

    4. Pruebas: demostrar que se cumplen los requisitos¶

    Las pruebas deben cubrir tanto casos correctos como situaciones de error.

    Caso de prueba Entrada o situación Resultado esperado
    CP-01 Clase con 3 plazas libres La reserva se acepta
    CP-02 Clase sin plazas libres La reserva se rechaza
    CP-03 El socio ya tiene una reserva para esa clase No se crea una reserva duplicada
    CP-04 Usuario sin autenticación Se deniega una operación protegida

    Ejemplo de prueba unitaria con JUnit 5:

    import static org.junit.jupiter.api.Assertions.*;
import org.junit.jupiter.api.Test;

class ReservaServiceTest {
    @Test
    void noPermiteReservarSinPlazas() {
        ReservaService servicio = new ReservaService();
        assertFalse(servicio.puedeReservar(0));
    }
}

    Este ejemplo presupone una clase ReservaService que contiene el método mostrado en la fase de implementación. Las pruebas unitarias verifican una parte aislada; las de integración comprueban, por ejemplo, la interacción con la base de datos.

    Herramientas habituales: JUnit, Mockito, Postman, Playwright y herramientas de depuración del IDE.

    5. Despliegue: llevar la aplicación a los usuarios¶

    Durante el desarrollo se suele distinguir entre:

    • Desarrollo: entorno local donde se programa.
    • Pruebas o preproducción: entorno de validación antes de publicar.
    • Producción: entorno real al que acceden los usuarios.

    Un flujo simplificado de entrega sería:

    flowchart TD
    A["Commit en Git"] --> B["Compilación"]
    B --> C["Pruebas automáticas"]
    C --> D["Generación del artefacto"]
    D --> E["Despliegue autorizado"]

    Herramientas habituales: GitHub Actions o Jenkins para automatización, Docker para empaquetar servicios y servidores Linux o plataformas de alojamiento para ejecutar la aplicación. No todo despliegue requiere contenedores ni automatización completa.

    6. Mantenimiento: corregir, adaptar y evolucionar¶

    Después de publicar, el gimnasio detecta que algunos socios quieren apuntarse a una lista de espera. Esto genera un nuevo requisito que puede requerir análisis, diseño, implementación, pruebas y una nueva versión.

    Además de los mantenimientos correctivo, adaptativo y perfectivo, se suele distinguir el preventivo, destinado a reducir riesgos futuros mediante mejoras internas, actualización de dependencias o refactorización.

    Herramientas habituales: GitHub Issues para incidencias, sistemas de registro (logs) y monitorización, y gestores de dependencias para actualizaciones.

    ¿Las fases siempre se realizan una sola vez?¶

    Las seis fases describen actividades del ciclo de vida, pero no obligan a utilizar una única metodología.

    Modelo tradicional en cascada Desarrollo iterativo y ágil
    Se planifica una secuencia de fases con entregables definidos Se trabaja en ciclos cortos y se revisan prioridades
    Los cambios tardíos pueden resultar costosos Se incorporan cambios según su valor y viabilidad
    Suele concentrar la validación formal después de la construcción Se busca validar y probar de forma frecuente
    Adecuado cuando los requisitos son estables y hay exigencias de planificación Adecuado cuando se necesita aprender del uso y adaptarse

    No confundir ciclo de vida y metodología

    Análisis, diseño, codificación, pruebas, despliegue y mantenimiento son actividades. Cascada, Scrum y Kanban son enfoques para organizar el trabajo. Scrum no elimina las fases: pueden repetirse dentro de cada Sprint, según el trabajo necesario.

    Ejemplo de desarrollo mediante Scrum¶

    En un primer Sprint, el equipo podría construir el listado de clases. En el siguiente, incorporar las reservas; en otro, las cancelaciones. Cada incremento debe cumplir los criterios de calidad acordados y ser utilizable, aunque todavía no incluya todas las funcionalidades previstas.

    Sprint Objetivo Resultado demostrable
    1 Consultar actividades Listado funcional
    2 Reservar plaza Reserva con control de aforo
    3 Cancelar reservas Gestión de reservas del usuario

    Documentación que se genera durante el desarrollo¶

    La documentación no pertenece exclusivamente a una fase: se crea y actualiza a lo largo del proyecto.

    Documento Utilidad
    Especificación de requisitos Acordar lo que debe hacer la aplicación
    Historias de usuario y criterios de aceptación Describir necesidades y cómo comprobarlas
    Diagramas UML y modelo de datos Comunicar el diseño
    README y documentación de API Facilitar la instalación y el uso técnico
    Plan y resultados de pruebas Registrar qué se ha verificado
    Manual de usuario Explicar cómo utilizar la aplicación
    Registro de incidencias y cambios Facilitar mantenimiento y trazabilidad

    Actividades¶

    AC 303 (RA1 / CE1b / IC1/ 3p). Una empresa tecnológica va a crear una aplicación móvil de gestión de tareas personales. Antes de comenzar a programar, el equipo se reúne para definir qué funciones debe tener la app, cómo se verá la interfaz, qué lenguaje utilizarán y cómo se probará antes de publicarla.

    1. Indica a qué fase del desarrollo del software pertenece cada una de las siguientes acciones:

      • Definir las funcionalidades y requisitos de la aplicación.
      • Crear diagramas UML para representar la arquitectura.
      • Escribir el código fuente de la aplicación.
      • Ejecutar pruebas de funcionamiento.
      • Subir la aplicación a la tienda de Android o iOS.
      • Actualizar la app corrigiendo errores detectados por los usuarios.

    2. Explica brevemente qué objetivo tiene cada una de esas fases dentro del proceso de desarrollo.

    AC 304 (RA1 / CE1b / IC1/ 3p). Imagina que formas parte del equipo que desarrolla una aplicación web para gestionar reservas en un gimnasio. Debes planificar el proceso completo de desarrollo, teniendo en cuenta todas las fases que has estudiado.

    1. Describe brevemente qué tareas realizarías en cada una de las siguientes fases:

      • Análisis de requisitos
      • Diseño del sistema
      • Implementación
      • Pruebas
      • Despliegue
      • Mantenimiento

    2. Menciona al menos una herramienta o tecnología que utilizarías en cada fase (por ejemplo, UML, Git, Visual Studio Code, Jenkins, etc.).

    3. Reflexiona: ¿qué fase crees que es más crítica para el éxito del proyecto y por qué?
