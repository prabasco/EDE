    Estructura de los equipos de trabajo en las fases del desarrollo de software¶

    El desarrollo de una aplicación no depende únicamente de escribir código. Requiere profesionales que colaboren para comprender las necesidades del cliente, diseñar la solución, implementarla, comprobar su calidad, desplegarla y mantenerla.

    Los roles representan responsabilidades, no necesariamente puestos de trabajo diferentes: en un proyecto pequeño, una persona puede asumir varias funciones; en uno grande, un mismo rol puede estar repartido entre varias personas.

    El siguiente esquema presenta las fases habituales de forma secuencial para facilitar su estudio. En los proyectos ágiles, muchas de estas actividades se solapan y se repiten en cada iteración.

    flowchart TD
    A["1. Análisis de requisitos"] --> B["2. Diseño del sistema"]
    B --> C["3. Implementación"]
    C --> D["4. Pruebas y verificación"]
    D --> E["5. Despliegue"]
    E --> F["6. Mantenimiento y mejora"]
    F -. "Nuevas necesidades" .-> A

    1. Análisis de requisitos¶

    El objetivo es identificar qué necesita el cliente, quién utilizará el sistema y qué condiciones debe cumplir. Los requisitos pueden ser funcionales (qué hace la aplicación) o no funcionales (seguridad, rendimiento, accesibilidad, etc.).

    • Analista de negocio o funcional (Business Analyst): recoge las necesidades del cliente, las aclara y las documenta como requisitos comprensibles y verificables. En algunas organizaciones esta función la desempeña un analista comercial, aunque ambos nombres no son siempre equivalentes.
    • Product Owner (PO): en Scrum, maximiza el valor del producto y se responsabiliza de gestionar y ordenar el Product Backlog; colabora en la aclaración de los requisitos.
    • Project Manager (jefe de proyecto): cuando existe este puesto, coordina la planificación, los recursos, los plazos y los riesgos del proyecto. No es un rol definido por Scrum.
    • Usuarios y cliente: aportan necesidades, restricciones y comentarios para comprobar que se está construyendo el producto adecuado.

    Ejemplo: aplicación de reservas

    El analista documenta que los clientes deben poder reservar y cancelar una cita; el Product Owner prioriza la reserva frente a funcionalidades secundarias; y el Project Manager, si existe, organiza los recursos y las fechas de entrega.

    2. Diseño del sistema¶

    Se define cómo se construirá la solución, tanto desde el punto de vista técnico como desde la experiencia de uso.

    • Arquitecto de software / Tech Lead: propone o guía las decisiones técnicas: componentes, arquitectura, tecnologías, comunicación entre servicios y persistencia de datos. Sus responsabilidades concretas varían según la organización.
    • Team Lead: facilita la coordinación del equipo y el reparto de responsabilidades cuando existe este puesto; puede participar también en las decisiones técnicas.
    • Diseñadores UX/UI: investigan necesidades de los usuarios, diseñan flujos de interacción, bocetos, prototipos e interfaces visuales.
    • Desarrolladores: aportan criterios de viabilidad técnica y ayudan a concretar las soluciones.

    Recordatorio

    UX se centra en la experiencia de uso y UI en el diseño de la interfaz. El diseño del sistema incluye también arquitectura, seguridad, datos y rendimiento; no se limita al aspecto visual.

    3. Implementación o desarrollo¶

    Los desarrolladores convierten los requisitos y el diseño en código ejecutable, integrando los diferentes componentes de la aplicación.

    • Desarrolladores Front-end: implementan la interfaz y su comportamiento en el cliente, especialmente en aplicaciones web.
    • Desarrolladores Back-end: implementan servicios, reglas de negocio, acceso a datos y mecanismos de seguridad del servidor.
    • Desarrolladores Full-stack: trabajan tanto en el front-end como en el back-end.
    • Desarrolladores móviles: crean aplicaciones para dispositivos móviles, por ejemplo con Kotlin y Jetpack Compose para Android.
    • Tech Lead / Team Lead: según la estructura del equipo, orientan decisiones técnicas, facilitan revisiones de código y ayudan a mantener criterios de calidad.

    Herramientas comunes

    Se utilizan IDE (Visual Studio Code, IntelliJ IDEA o Android Studio), Git para el control de versiones y plataformas de colaboración como GitHub o GitLab. Las pull requests permiten proponer y revisar cambios antes de integrarlos.

    Ejemplo

    En una aplicación de reservas, el front-end muestra el formulario, el back-end comprueba la disponibilidad y la base de datos almacena las reservas. En una aplicación Android, el desarrollador móvil implementa la interfaz y se comunica con una API REST.

    4. Pruebas y verificación¶

    Se comprueba que el software funciona según lo esperado, cumple los requisitos y presenta un nivel de calidad adecuado. Las pruebas no se realizan únicamente al final: también pueden ejecutarse durante la implementación y de forma automatizada.

    • Desarrolladores: crean y ejecutan pruebas unitarias y colaboran en pruebas de integración, entre otras.
    • QA Testers / profesionales de calidad: diseñan casos de prueba, comprueban comportamientos, registran defectos y colaboran en pruebas funcionales, de integración y de sistema.
    • Product Owner y usuarios implicados: ayudan a comprobar que el resultado satisface las necesidades y los criterios de aceptación establecidos.
    • Tech Lead: ayuda a definir prácticas de calidad técnica y estrategias de pruebas cuando corresponde.

    No confundir responsabilidades

    El Scrum Master no es un tester ni el responsable de aprobar las pruebas. En Scrum, facilita la aplicación del marco de trabajo, ayuda a eliminar impedimentos y contribuye a la eficacia del equipo. Del mismo modo, un Project Manager no es automáticamente quien valida los criterios de aceptación funcionales.

    Ejemplo

    Para una reserva, se prueba que no puedan asignarse dos citas al mismo recurso y horario, que se informe de los errores y que la cancelación actualice correctamente los datos.

    5. Despliegue¶

    Consiste en poner una versión de la aplicación a disposición de los usuarios, normalmente en un entorno de producción. Puede realizarse de forma manual o mediante procesos automatizados de integración y entrega continua (CI/CD).

    • Profesionales DevOps / operaciones / administradores de sistemas: colaboran en la automatización, la infraestructura, la configuración y la monitorización del despliegue. DevOps es también un conjunto de prácticas y una cultura de colaboración, no necesariamente un cargo.
    • Desarrolladores: preparan la aplicación, sus dependencias y los cambios necesarios para su publicación.
    • Project Manager: cuando existe, coordina calendarios, dependencias y comunicación de la entrega.
    • Product Owner y responsables autorizados: revisan el alcance funcional y participan en las decisiones de publicación según el procedimiento de la organización. La aprobación formal no corresponde siempre al mismo rol.

    Ejemplo

    En una aplicación web se publica la nueva versión en un servidor, se aplican las migraciones necesarias de la base de datos y se comprueba que el servicio responde correctamente. Conviene disponer de monitorización y de un plan de reversión ante fallos.

    6. Mantenimiento y mejora continua¶

    Después del despliegue, el producto necesita corrección de defectos, actualizaciones de seguridad, adaptación a cambios y nuevas funcionalidades.

    • Desarrolladores: diagnostican incidencias, corrigen errores, actualizan dependencias y mejoran el rendimiento.
    • Tech Lead / arquitecto: analiza el impacto técnico de los cambios importantes y la evolución de la arquitectura.
    • Product Owner: revisa las nuevas necesidades y reordena el Product Backlog cuando se trabaja con Scrum.
    • QA: verifica las correcciones y realiza pruebas de regresión.
    • Operaciones / DevOps: monitoriza el servicio y colabora en la respuesta ante incidencias.
    • Scrum Master: si el equipo utiliza Scrum, facilita la mejora continua de su forma de trabajo; no dirige técnicamente el mantenimiento.

    Buena práctica

    Documentar las incidencias, utilizar un sistema de seguimiento de tareas y mantener el control de versiones facilita la evolución del software.

    Relación global entre fases y roles¶

    La siguiente imagen muestra una asociación simplificada de perfiles y fases. No implica que cada profesional participe exclusivamente en una etapa ni que las funciones sean idénticas en todas las empresas.

    Tabla resumen¶

    Fase Perfiles habituales Responsabilidad principal
    Análisis Analista de negocio, Product Owner, Project Manager Recoger y priorizar necesidades; planificar el proyecto cuando proceda.
    Diseño Arquitecto / Tech Lead, UX/UI, desarrolladores, Team Lead Definir la arquitectura, la interfaz y las soluciones técnicas.
    Implementación Desarrolladores, Tech Lead / Team Lead Programar, integrar y revisar el código.
    Pruebas Desarrolladores, QA, Product Owner Comprobar la calidad técnica y el cumplimiento de requisitos.
    Despliegue Operaciones / DevOps, desarrolladores, responsables de entrega Publicar y verificar la versión en producción.
    Mantenimiento Desarrolladores, QA, operaciones, Tech Lead, Product Owner Corregir incidencias y evolucionar el producto.

    Diferencias entre roles de coordinación¶

    Rol Enfoque principal Aclaración
    Product Owner Valor del producto y orden del Product Backlog. Es una responsabilidad definida en Scrum.
    Scrum Master Eficacia del equipo Scrum y correcta comprensión y aplicación de Scrum. No asigna tareas por definición ni sustituye al Project Manager.
    Project Manager Planificación y gestión del proyecto, recursos y riesgos. No es uno de los tres roles o responsabilidades definidos por Scrum.
    Tech Lead Orientación técnica, arquitectura y calidad del código. Su alcance depende de la empresa.
    Team Lead Coordinación y acompañamiento del equipo. Puede coincidir con el Tech Lead en equipos pequeños.

    Equipos tradicionales y ágiles

    En un modelo secuencial, las fases suelen representarse como etapas diferenciadas. En un modelo incremental o ágil, el equipo puede analizar, diseñar, implementar y probar en cada entrega. Scrum define tres responsabilidades (Product Owner, Scrum Master y Developers); otros puestos de la empresa pueden existir, pero no son responsabilidades adicionales de Scrum.

    Conclusión

    Los equipos se organizan según el tamaño, la metodología y las necesidades del proyecto. Lo importante es comprender las responsabilidades y cómo colaboran, no memorizar una estructura fija aplicable a todas las empresas.

    Actividades¶

    AC 305. Análisis de roles en las fases del desarrollo¶

    RA1 / CE1b / IC1 / 3 puntos. Analiza los roles del equipo de desarrollo en cada fase del ciclo de vida del software.

    1. Elabora una tabla que relacione las seis fases (análisis, diseño, implementación, pruebas, despliegue y mantenimiento) con los perfiles que intervienen en ellas.
    2. Para cada relación, explica en una línea qué aporta ese perfil.
    3. Incluye al menos un ejemplo real o simulado (app móvil, web o sistema de gestión) que muestre la colaboración entre dos roles.
    4. Explica por qué un mismo profesional puede intervenir en varias fases.

    Consejo

    Puedes utilizar diagrams.net (Draw.io), Canva o una tabla Markdown. Justifica las relaciones, no te limites a enumerar nombres.

    AC 306. Organización simulada de un equipo de desarrollo¶

    RA1 / CE1b / IC1 / 3 puntos. Simula la organización de un equipo de desarrollo para un proyecto.

    1. Imagina que tu equipo desarrollará una aplicación sencilla (reservas, recetas o blog personal).

    2. Reparte entre los integrantes las siguientes responsabilidades simuladas (una persona puede asumir varias):

      • Product Owner.
      • Project Manager.
      • Analista de negocio o funcional.
      • Desarrollador Front-end.
      • Desarrollador Back-end.
      • Diseñador UX/UI.
      • Scrum Master, solo si se decide simular el uso de Scrum.

    3. Describe las tareas concretas de cada participante en las distintas fases del proyecto.

    4. Dibuja un esquema que represente la comunicación y la colaboración entre los perfiles.
    5. Indica quién comprobaría los criterios de aceptación y quién se encargaría del despliegue técnico, aunque esas responsabilidades deban asignarse a perfiles adicionales o compartirse.

    Ejemplo

    Durante el diseño, el Tech Lead propone la arquitectura, el diseñador UX/UI prepara el prototipo y el Product Owner aclara y prioriza las necesidades. Posteriormente, los desarrolladores implementan las funciones y comprueban su funcionamiento con ayuda de QA, si existe ese perfil.
