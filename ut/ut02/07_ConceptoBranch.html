    Concepto de ramas (branch) en Git¶

    Antes de analizar el estado de un repositorio, es necesario entender qué es una rama (branch), un concepto fundamental en Git.

    Las ramas permiten trabajar en distintas versiones de un proyecto de forma independiente, sin modificar directamente el código de la rama principal.

    Cómo Git almacena los datos¶

    A diferencia de otros sistemas que almacenan los cambios de forma incremental, Git guarda instantáneas del proyecto (snapshots) en cada confirmación.

    Git no necesita duplicar los archivos que no han cambiado, ya que puede reutilizar los objetos almacenados anteriormente.

    Cada confirmación o commit contiene:

    • Una referencia al árbol que representa los archivos del proyecto.
    • Metadatos: autor, fecha y mensaje.
    • Referencias a commits anteriores (uno o varios si es una fusión).

    Ejemplo inicial:

    git add README test.rb LICENSE
git commit -m "Initial commit of my project"

    Tras esta confirmación, suponiendo que los tres archivos tengan contenidos diferentes, Git crea:

    • Un objeto blob por cada archivo, que almacena su contenido.
    • Un objeto tree que representa la estructura del directorio.
    • Un objeto commit que apunta al árbol creado.

    El repositorio contendrá cinco objetos: tres blobs, un árbol y un commit.

    Qué es una rama¶

    Una rama en Git es un apuntador móvil que señala un commit determinado.

    La rama principal suele llamarse main, aunque en repositorios antiguos puede denominarse master.

    Cada vez que realizamos un commit, la rama activa avanza automáticamente al nuevo commit.

    Main y master

    main y master son nombres convencionales para la rama principal. Ninguno tiene un comportamiento especial.

    Actualmente es habitual utilizar main. En estos ejemplos utilizaremos master.

    Crear una nueva rama¶

    Para crear una nueva rama:

    git branch testing

    Esto crea una rama llamada testing, que inicialmente apunta al mismo commit que la rama actual.

    Importante

    El comando git branch testing crea la rama, pero no cambia automáticamente a ella.

    Git utiliza una referencia especial llamada HEAD para indicar la posición actual del repositorio.

    Normalmente, HEAD apunta a la rama activa, por ejemplo, master o testing.

    Podemos consultar las referencias mediante:

    git log --oneline --decorate

    Ejemplo de salida:

    f30ab (HEAD -> master, testing) add feature #32
34ac2 fixed bug #1328
98ca9 initial commit of my project

    En este momento:

    • HEAD indica que estamos trabajando en master.
    • master y testing apuntan al mismo commit.
    • Todavía no existen diferencias entre ambas ramas.

    Consultar las ramas existentes¶

    Para visualizar todas las ramas locales:

    git branch

    Ejemplo:

    * master
  testing

    El asterisco * indica la rama activa.

    Para mostrar también las ramas remotas:

    git branch -a

    Cambiar de rama¶

    Para cambiar a otra rama utilizamos:

    git switch testing

    También podemos utilizar el comando tradicional:

    git checkout testing

    Ahora HEAD apunta a testing.

    Podemos comprobarlo mediante:

    git branch

    Resultado:

      master
* testing

    Si modificamos un archivo y confirmamos los cambios:

    git add .
git commit -m "Cambios realizados en testing"

    La rama testing avanzará al nuevo commit, mientras que master permanecerá en su posición anterior.

    Para regresar a la rama principal:

    git switch master

    Esto provoca que:

    • HEAD vuelva a apuntar a master.
    • El directorio de trabajo se actualice con los archivos correspondientes a esa rama.
    • Los commits exclusivos de testing no aparezcan todavía en master.

    Cambios sin confirmar

    Cambiar de rama puede modificar los archivos del directorio de trabajo.

    Si existen cambios sin confirmar que podrían sobrescribirse, Git puede impedir el cambio.

    Antes de cambiar de rama es recomendable comprobar el estado del repositorio:

    git status

    Crear una rama y cambiar directamente a ella¶

    Podemos realizar ambas operaciones mediante:

    git switch -c desarrollo

    Equivale a ejecutar:

    git branch desarrollo
git switch desarrollo

    Trabajando con varias ramas¶

    Podemos trabajar de forma independiente en distintas ramas.

    Por ejemplo, mientras estamos en testing, realizamos un commit:

    git add .
git commit -m "Nueva funcionalidad"

    Después regresamos a master:

    git switch master

    Realizamos otros cambios y confirmamos:

    git add .
git commit -m "Corrección de errores"

    Ahora el historial de commits se ha dividido:

    • testing contiene los cambios de la nueva funcionalidad.
    • master contiene los cambios correspondientes a la corrección de errores.

    Para visualizar todas las ramas y sus commits:

    git log --oneline --decorate --graph --all

    Ejemplo:

    * c2b9e (HEAD -> master) Corrección de errores
| * 87ab2 (testing) Nueva funcionalidad
|/
* f30ab add feature #32
* 34ac2 fixed bug #1328
* 98ca9 initial commit of my project

    Las dos ramas comparten un historial inicial, pero tienen commits diferentes.

    Fusionar ramas (merge)¶

    Una vez que hemos terminado de trabajar en una rama, podemos incorporar sus cambios a la rama principal.

    Esta operación se denomina fusión o merge.

    El comando utilizado es:

    git merge nombre-rama

    Regla fundamental

    Debemos situarnos primero en la rama que recibirá los cambios.

    Si queremos incorporar los cambios de testing a master, debemos estar en master antes de realizar la fusión.

    1. Cambiar a la rama principal¶

    git switch master

    Comprobamos la rama activa:

    git branch

    Resultado:

    * master
  testing

    2. Fusionar la rama testing¶

    Ejecutamos:

    git merge testing

    Git incorpora a master los cambios confirmados en testing.

    Si las ramas han evolucionado de forma independiente, Git puede generar un nuevo commit de fusión.

    El historial podría quedar así:

    *   a83fd (HEAD -> master) Merge branch 'testing'
|\
| * 87ab2 (testing) Nueva funcionalidad
* | c2b9e Corrección de errores
|/
* f30ab add feature #32
* 34ac2 fixed bug #1328
* 98ca9 initial commit of my project

    Ahora master incorpora los cambios de ambas ramas.

    Tipos de fusión

    Git puede realizar diferentes tipos de fusión:

    • Fast-forward: cuando la rama de destino no tiene commits nuevos desde que se creó la otra rama. Git simplemente mueve el apuntador.
    • Three-way merge: cuando ambas ramas tienen commits diferentes. Git combina sus cambios y normalmente crea un nuevo commit de fusión.

    3. Fusionar todas las ramas en master¶

    Si tenemos varias ramas, debemos fusionarlas individualmente.

    Por ejemplo:

    master
testing
desarrollo
correcciones

    Primero nos situamos en la rama principal:

    git switch master

    Después fusionamos cada rama:

    git merge testing
git merge desarrollo
git merge correcciones

    Una vez completadas correctamente las fusiones, master incorporará los cambios confirmados de todas ellas.

    Podemos comprobar el historial:

    git log --oneline --decorate --graph --all

    Importante

    Fusionar ramas no significa que todos los archivos existentes en cualquier rama deban conservarse necesariamente.

    Git combina los cambios y también tiene en cuenta los archivos eliminados o renombrados.

    Además, git merge incorpora commits confirmados, no cambios sin confirmar.

    Resolver conflictos durante una fusión¶

    Un conflicto de fusión aparece cuando Git no puede combinar automáticamente determinados cambios.

    Por ejemplo, si modificamos la misma línea de un archivo en master y testing.

    Al ejecutar:

    git merge testing

    Git puede mostrar:

    CONFLICT (content): Merge conflict in Main.java
Automatic merge failed; fix conflicts and then commit the result.

    1. Identificar los archivos en conflicto¶

    git status

    2. Abrir el archivo y resolver el conflicto¶

    Git añade marcas similares a estas:

    <<<<<<< HEAD
System.out.println("Versión master");
=======
System.out.println("Versión testing");
>>>>>>> testing

    Debemos decidir qué código conservar, combinar las modificaciones si es necesario y eliminar las marcas de conflicto.

    3. Confirmar la resolución¶

    Después de guardar el archivo:

    git add Main.java
git commit -m "Resolver conflicto de fusión"

    La fusión quedará completada.

    Cancelar una fusión

    Si queremos cancelar una fusión que todavía está en curso:

    git merge --abort

    Git intentará restaurar el estado anterior a la fusión.

    Eliminar una rama¶

    Cuando una rama ya ha cumplido su función y sus cambios se han incorporado a master, podemos eliminarla.

    1. Comprobar la rama activa¶

    git branch

    Ejemplo:

    * master
  testing
  test

    Importante

    No podemos eliminar una rama mientras estamos situados en ella.

    Antes debemos cambiar a otra rama:

    git switch master

    2. Eliminar la rama test¶

    Para eliminar la rama local llamada test:

    git branch -d test

    La opción -d elimina la rama si Git considera que sus cambios están correctamente integrados en el historial de la rama de referencia.

    Si la rama contiene commits que no han sido fusionados, Git puede impedir su eliminación para evitar pérdidas accidentales.

    Forzar la eliminación

    También podemos eliminar una rama utilizando:

    git branch -D test

    La opción -D fuerza la eliminación de la rama, incluso si contiene commits que todavía no han sido fusionados.

    No debemos utilizar esta opción si queremos conservar los cambios pendientes.

    3. Comprobar que la rama ha desaparecido¶

    git branch

    Resultado:

    * master
  testing

    La rama test ya no existe en el repositorio local.

    Eliminar una rama no elimina sus commits fusionados

    Cuando eliminamos una rama que ya ha sido fusionada, los cambios incorporados a master permanecen en el repositorio.

    Lo que eliminamos es el apuntador que identificaba esa rama.

    4. Eliminar una rama remota¶

    Si la rama también existe en un repositorio remoto llamado origin, podemos eliminarla mediante:

    git push origin --delete test

    Este comando elimina la rama del repositorio remoto, pero no modifica la rama local.

    Ejemplo práctico completo¶

    Vamos a realizar un ejercicio que incluya la creación, modificación, fusión y eliminación de una rama.

    Paso 1. Crear un repositorio¶

    mkdir proyecto-git
cd proyecto-git
git init -b master

    Creamos un archivo desde CMD de Windows:

    echo Proyecto inicial > README.md

    Lo añadimos al repositorio y confirmamos:

    git add .
git commit -m "Primer commit"

    Paso 2. Crear una rama test¶

    git switch -c test

    Creamos un nuevo archivo:

    echo Archivo de pruebas > pruebas.txt

    Confirmamos los cambios:

    git add .
git commit -m "Añadir archivo de pruebas"

    Paso 3. Regresar a master¶

    git switch master

    Si consultamos los archivos del directorio, observaremos que pruebas.txt no aparece, porque pertenece al estado confirmado en la rama test.

    Paso 4. Fusionar test con master¶

    git merge test

    Ahora master incorpora el archivo pruebas.txt.

    Podemos comprobarlo mediante:

    git status
git log --oneline --graph --all

    Paso 5. Eliminar la rama test¶

    git branch -d test

    Paso 6. Comprobar el resultado¶

    git branch

    Resultado:

    * master

    Y si consultamos los archivos:

    dir

    Encontraremos:

    README.md
pruebas.txt

    Resultado final:

    • Hemos creado una rama test.
    • Hemos trabajado de forma independiente en ella.
    • Hemos fusionado sus cambios en master.
    • Hemos eliminado la rama test.
    • Los archivos y commits fusionados siguen formando parte del proyecto.

    Ventajas de las ramas en Git¶

    Las ramas en Git son ligeras y rápidas, porque una rama local es esencialmente una referencia a un commit.

    Crear una rama no implica copiar todos los archivos del proyecto.

    Gracias a esto:

    • Desarrollo independiente: permite implementar funcionalidades sin modificar directamente la rama principal.
    • Trabajo en equipo: distintos desarrolladores pueden trabajar en ramas diferentes.
    • Corrección de errores: permite crear ramas específicas para solucionar problemas.
    • Experimentación: podemos probar nuevas ideas sin comprometer la versión principal.
    • Integración de cambios: mediante git merge podemos incorporar el trabajo realizado.
    • Organización: facilita mantener una rama estable y otras destinadas al desarrollo.

    Resumen de comandos

    Comando Función
    git branch Mostrar ramas locales
    git branch -a Mostrar ramas locales y remotas
    git branch test Crear la rama test
    git switch test Cambiar a la rama test
    git switch -c test Crear y cambiar a test
    git switch master Cambiar a master
    git merge test Fusionar test en la rama actual
    git branch -d test Eliminar test de forma segura
    git branch -D test Forzar la eliminación de test
    git push origin --delete test Eliminar la rama remota test
    git log --oneline --graph --all Visualizar el historial de todas las ramas
